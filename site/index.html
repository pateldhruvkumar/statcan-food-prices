StatCan Food Prices Pipeline

A batch pipeline that turns two Statistics Canada tables into a Power BI report on grocery prices. Python splits the raw CSV downloads into yearly files, the files land in Amazon S3, Snowflake loads them through a storage integration, and dbt models them into bronze, silver and gold tables.

  • pandas

  • Amazon S3
  • AWS IAM

Source code on GitHub

Overview

Statistics Canada publishes the monthly average retail price of 110 grocery and household products, along with the monthly Consumer Price Index. Each table comes as one large CSV with every month and region stacked together, and neither one shows how prices change from one month or year to the next.

I built this pipeline to answer three questions in Power BI:

  • How much did a product's price change since last month in a given province?
  • How does the change from the same month last year compare across provinces?
  • Which 10 products went up the most in Canada over the past year?

Split the raw files by year

Python, pandas · start/split_data.py

The two downloads are 19 MB and 161 MB. I split each one into one file per year, so a single year can be uploaded and loaded on its own and the S3 layout can be partitioned by year.

split_data.py reads both CSVs with pandas. For each year from 2017 to 2026 it keeps the rows whose REF_DATE starts with that year and writes them under data/loading/. The CPI table goes back to January 1914, so the same loop also trims it to the ten years the price table covers.

start/split_data.py

for year in range(start_year, end_year + 1):
    avg_by_year[year] = df_average[
        df_average['REF_DATE'].str.startswith(str(year))
    ].copy()
    cpi_by_year[year] = df_provience[
        df_provience['REF_DATE'].str.startswith(str(year))
    ].copy()

    avg_count = avg_count + len(avg_by_year[year])
    cpi_count = cpi_count + len(cpi_by_year[year])

Land the files in Amazon S3

boto3, IAM user · src/ingestion/upload_to_s3.py

The yearly files go into an S3 bucket named stats-canada-grocery-data, under a landing/ prefix. Each dataset has its own folder, and each year sits in its own Hive-style year= partition.

Bucket layout

s3://stats-canada-grocery-data/
└── landing/
    ├── average-price/
    │   ├── year=2017/average-price_2017.csv
    │   ├── ...
    │   └── year=2026/average-price_2026.csv
    └── cpi/
        ├── year=2017/provience-price_2017.csv
        ├── ...
        └── year=2026/provience-price_2026.csv

upload_to_s3.py builds the object key from the dataset name and the year, checks that the local file exists, and uploads it with boto3. It catches ClientError and BotoCoreError, prints what failed and raises again, so a failed upload stops the run. The YEAR constant at the top sets which year to send.

src/ingestion/upload_to_s3.py

s3_key = f"landing/{dataset_name}/year={year}/{local_file.name}"

try:
    s3_client.upload_file(
        Filename=str(local_file),
        Bucket=BUCKET_NAME,
        Key=s3_key
    )

    print(f"Uploaded: {local_file.name}")
    print(f"S3 location: s3://{BUCKET_NAME}/{s3_key}")

except (ClientError, BotoCoreError) as error:
    print(f"Upload failed for {local_file.name}")
    print(error)
    raise

IAM user for the upload

The script runs as a dedicated IAM user instead of the AWS root account.

  • The user has an access key for programmatic access.
  • The key is stored in the local AWS credentials file with aws configure. boto3 picks it up through its default credential chain, so there are no keys in the code or in the repository.
  • Its policy only allows uploads into the landing/ prefix.

IAM policy on the upload user

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::stats-canada-grocery-data/landing/*"
    }
  ]

Connect Snowflake to S3 and load

IAM role, storage integration, COPY INTO · snowflake/load_average_price.sql · snowflake/load_cpi.sql

Snowflake reads the bucket through a storage integration called STATSCAN_S3_INT. The integration holds the ARN of an IAM role. When a stage needs to list or read files, Snowflake's own AWS identity assumes that role and works with its temporary credentials. No AWS keys are stored in Snowflake or written into the SQL.

Setting up the IAM role and the integration

The role and the integration each need a value from the other, so the setup went back and forth between AWS and Snowflake:

  1. Created an IAM policy that allows s3:GetObject and s3:GetObjectVersion on landing/*, and s3:ListBucket and s3:GetBucketLocation on the bucket.
  2. Created an IAM role for Snowflake and attached that policy.
  3. Created the storage integration STATSCAN_S3_INT in Snowflake with the role's ARN, limited to s3://stats-canada-grocery-data/landing/.
  4. Ran DESC INTEGRATION STATSCAN_S3_INT and copied STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID.
  5. Updated the role's trust policy with those two values. Only Snowflake's identity can assume the role, and only when it passes that external ID.
  6. Created the stage STATSCAN_S3_STAGE on top of the integration.

Snowflake worksheet

CREATE STORAGE INTEGRATION STATSCAN_S3_INT
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::<aws_account_id>:role/<snowflake_role>'
  STORAGE_ALLOWED_LOCATIONS = ('s3://stats-canada-grocery-data/landing/');

DESC INTEGRATION STATSCAN_S3_INT;
-- STORAGE_AWS_IAM_USER_ARN: Principal in the role's trust policy
-- STORAGE_AWS_EXTERNAL_ID:  sts:ExternalId condition in the trust policy

Loading with COPY INTO

Both load scripts run in STATSCAN_ANALYTICS.SOURCE and follow the same four steps. This is the average price script. The CPI one changes only the table name and the cpi/ folder.

snowflake/load_average_price.sql

USE SCHEMA STATSCAN_ANALYTICS.SOURCE;

-- 1. Stage: points to the S3 folder
CREATE STAGE IF NOT EXISTS STATSCAN_S3_STAGE
  URL = 's3://stats-canada-grocery-data/landing/'
  STORAGE_INTEGRATION = STATSCAN_S3_INT;

-- 2. File format: CSV with a header row
CREATE FILE FORMAT IF NOT EXISTS STATSCAN_CSV
  TYPE = CSV
  PARSE_HEADER = TRUE
  FIELD_OPTIONALLY_ENCLOSED_BY = '"';

-- 3. Table: columns are taken from the CSV header
CREATE TABLE IF NOT EXISTS SOURCE_AVERAGE_PRICE
  USING TEMPLATE (
    SELECT ARRAY_AGG(OBJECT_CONSTRUCT(*))
    FROM TABLE(INFER_SCHEMA(
      LOCATION => '@STATSCAN_S3_STAGE/average-price/',
      FILE_FORMAT => 'STATSCAN_CSV')));

-- 4. Load the data
COPY INTO SOURCE_AVERAGE_PRICE
  FROM @STATSCAN_S3_STAGE/average-price/
  FILE_FORMAT = (FORMAT_NAME = 'STATSCAN_CSV')
  MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;
  • INFER_SCHEMA reads the CSV header and CREATE TABLE ... USING TEMPLATE builds the table from it, so there is no hand-written DDL. Header names are kept as they are, which is why a column like "Products and product groups" needs double quotes later in dbt.
  • MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE matches CSV columns to table columns by name instead of by position.
  • Snowflake keeps 64 days of load history for each table, so running COPY INTO again after a new upload loads only the new file.

With all ten years uploaded, SOURCE_AVERAGE_PRICE has 141,432 rows and SOURCE_CPI has 236,180.

Model the data with dbt

dbt Core, dbt-snowflake · statscan_dbt/

dbt reads the two SOURCE tables declared in sources.yml and builds three layers, each in its own schema. Every model is materialized as a table. The connection profile points at the STATSCAN_ANALYTICS database and the STATSCAN_WH warehouse, and it stays out of Git along with every other credential file.

LayerModelsWhat happens
Bronze bronze_average_price
bronze_cpi		 SELECT * from the two source tables. Every later model reads from bronze, never from SOURCE directly.
Silver silver_average_price
silver_cpi		 TRY_TO_DATE turns REF_DATE values like 2017-01 into real dates. Columns are renamed and cast, and VALUE becomes NUMBER(6,2) through TRY_CAST, so a bad value turns into NULL instead of failing the run.
Gold Five models, listed below Window functions over silver_average_price that answer the report's questions.

Schema names

By default dbt puts the target schema in front of a custom schema name, which here would give SILVER_BRONZE and SILVER_GOLD. A small override of generate_schema_name returns the custom name unchanged, so the models land in BRONZE, SILVER and GOLD.

statscan_dbt/macros/generate_schema.sql

{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if custom_schema_name is none -%}
        {{ default_schema }}
    {%- else -%}
        {{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

Gold models

ModelQuestionHow
price_change_over_months How much did the price move since last month? LAG(average_price) for each province and product, then the change in dollars and percent.
price_change_over_years How much did it move since the same month last year? LAG(average_price, 12) over the same partition.
biggest_price_change_for_ten_products Which ten products rose the most in Canada over the year? Latest month and Canada only, ranked by percent change with DENSE_RANK(), top 10 kept.
most_expensive_provience Which three provinces charge the most for each product? DENSE_RANK() on price within each product for the latest month, with Canada left out.
rolling_average_price What does the trend look like without the monthly noise? 3-month and 12-month moving averages over ROWS BETWEEN window frames.

statscan_dbt/models/gold/price_change_over_years.sql

WITH price_change_over_year AS
(
    SELECT
        reference_date,
        geography_location,
        products,
        average_price,
        LAG(average_price, 12) OVER (
            PARTITION BY geography_location, products
            ORDER BY reference_date
        ) AS prev_year_price
    FROM
        {{ ref('silver_average_price') }}
)
SELECT
    reference_date,
    geography_location,
    products,
    average_price,
    prev_year_price,
    average_price - prev_year_price AS price_change,
    ROUND((average_price - prev_year_price)
        / NULLIF(prev_year_price, 0) * 100, 2) AS precentage_change
FROM
    price_change_over_year
  • LAG(average_price, 12) steps back 12 rows. Each of the 1,308 product and region series is an unbroken run of months, so 12 rows back is always the same month a year earlier.
  • Percent changes divide by NULLIF(previous price, 0), so a zero price returns NULL instead of a division error.
  • The moving averages only appear when the window is full. COUNT(average_price) skips NULLs, so a window that includes one of the 34 missing prices stays empty instead of averaging fewer months.

Report in Power BI

Power BI Desktop · power_bi/power_bi_dashboard.pbix

Power BI connects to Snowflake and brings all five gold tables into its model. Three lookup tables, Product Lookup, Province Lookup and Date Lookup, feed the slicers.

The three cards read from PRICE_CHANGE_OVER_MONTHS and show the selected product's price for the chosen month and province, the price one month earlier, and the change in dollars. The bar chart compares the year-over-year percent change across provinces, using PRICE_CHANGE_OVER_YEARS. The table lists the ten biggest year-over-year increases in Canada.
